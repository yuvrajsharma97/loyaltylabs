Grounded in the repo
Three entry points, as in TillHome — scan a QR, type the customer's code, redeem a code — plus the identify → earn → success and redeem → result paths. Verification method is shown. The API records whether identification came from a scan or a manual code, so the earn screen states which one it's about to send. Every failure branch is drawn — camera refused, code not found, redemption expired (amber), redemption rejected (red) — with the source's own severity split. The points cap note survives on the success screen, shown only when the cap actually bit.
Changed, and why
The till code is entered once per shift, not once per action. Source asks for it on the lookup, on the earn, and on the redeem — three PIN entries per customer, dozens of times a day, in front of a queue. Here it unlocks the till and the app bar shows who's on. Except giving a reward, which spends points irreversibly and still re-checks. Attribution is unaffected: each scan is still recorded against the code that unlocked the till. Amount and PIN use a keypad, not a text field. A staff phone on a counter is tapped, not typed into — and a big numeric pad is faster and less error-prone than a spinner input. The amount screen previews the points before you commit. The primary button reads "Award 12 points", so a mistyped amount is caught before it lands. Scan failure offers the fallback in place rather than dumping staff back to the menu with a toast. Success ends with "Next customer". The queue is the context; going back to the menu is the secondary action.
